# 保研顾问 Agent 细致版方案

## 1. 这版优化解决什么问题
当前的一期方案已经覆盖了保研顾问的核心能力，但在真实落地时，还缺少三层“产品级安全垫”：

1. **部署前环境排查层**  
   先看用户现有 OpenCode 生态栈里已经有什么，避免重复安装、工具冲突、权限过宽。

2. **生态组件推荐层**  
   不是简单告诉用户“去装插件”，而是根据项目目标和现有环境，给出“必装 / 强烈建议 / 可选 / 暂不建议”的分层推荐。

3. **GitHub 组件接入判定层**  
   不能把任意 GitHub 仓库都当成可调用能力。必须先判断该组件能否以 plugin / MCP / custom tool / GitHub agent 的方式接入，再谈复用。

## 3. 为什么要加 stack-auditor
本项目不是一个只在单机上自己玩的 agent，而是准备给同学使用、后续可能商业化。  
这种情况下，如果不先排查用户当前环境，就会遇到这些现实问题：

- 用户已经有全局级 OpenCode agents，与你的项目角色冲突
- 用户已经装了同类 MCP，重复接入后工具选择混乱
- 用户已经有大型插件包，默认 hook 会影响你项目行为
- 用户把某个 GitHub 仓库误以为“直接可调用 agent”
- 用户的 provider / model / auth 根本还没配好

所以部署前先审计，再推荐，再询问是否安装，是这版优化里最重要的一步。

---

## 4. 真实可落地的推荐策略

### 4.1 默认原则
1. **内置能力先行**
   - OpenCode 自带 `websearch`、`webfetch`、agents、commands、custom tools、MCP 接入能力。
   - 先用这些跑通主链，不要一上来装很多第三方组件。

2. **按能力缺口补，而不是按“看起来很强”补**
   - 缺动态网页抓取 -> 再上 Playwright MCP
   - 缺 GitHub 仓库自动化 -> 再上 GitHub agent / GitHub MCP
   - 缺成本优化 -> 再看认证/计费类插件
   - 缺远程隔离环境 -> 再看 sandbox 类插件

3. **第三方仓库先判接入路径，再判价值**
   - 能接成 plugin / MCP / custom tool / GitHub agent 才算可接入
   - 不能只因为“GitHub 上很火”就纳入默认栈

## 5.2 强烈建议项
### A. Playwright MCP
适用场景：
- 学校官网、实验室主页、导师主页里有大量 JS 动态内容
- 纯 `webfetch` 拿不到关键信息
- 页面需要真实浏览器交互

价值：
- 对保研场景非常实用，因为不少学院通知页、实验室站点、嵌套页面、跳转页面不够静态

风险：
- 相比内置 web 工具更重
- 会引入浏览器自动化复杂度

### B. GitHub MCP server
适用场景：
- 你希望 agent 不只写本地文件，还能读 repo、issue、PR、workflow

价值：
- 让你的 agent 更像一个“持续演进的工程系统”，而不是一次性脚手架

风险：
- 应该限制 toolsets，不要全开

---

## 5.3 可选项
### C. opencode-openai-codex-auth
适用场景：
- 你希望在一定条件下优化模型使用成本
- 你已经有对应订阅，愿意按该路径配置

价值：
- 成本优化，不是功能核心

## 5.4 暂不建议默认安装
### F. 大而全的第三方插件包
比如一类“自带很多 agents / MCP / AST / LSP / hook”的重型插件包

## 6. 如何处理 GitHub 上的“优秀插件 / agent”
这部分必须讲得现实一点：

### 6.1 不能直接调用任意 GitHub 仓库
一个 GitHub 仓库只有在满足以下之一时，才应视为“可接入”：
- 本身是 OpenCode plugin
- 本身是 MCP server
- 能被改造成 `.opencode/tools/` 的 custom tool
- 能通过 OpenCode GitHub agent / GitHub Actions 工作流接入

### 6.2 推荐接入流程
1. 识别仓库类型
2. 确认安装路径
3. 确认权限边界
4. 确认维护活跃度
5. 判断是否与保研项目真的相关
6. 生成“是否纳入”的结论

### 6.3 默认拒绝条件
- 安装方式不清楚
- 权限要求过大
- 与内置能力严重重叠
- 项目维护明显停滞
- 需要额外云服务或订阅而用户并不想开

---

## 7.  agent 应该怎么和用户交互
你要求的是：
> 在部署我的方案前对用户现有插件进行排查，之后出一套方案询问用户是否安装最适合我项目的插件或者 agent。

所以推荐交互必须长这样：

### 第一步：先排查
“我先检查你当前项目级和全局级的 OpenCode 配置、plugins、agents、tools、MCP，再判断是否已经具备保研项目所需能力。”

### 第二步：再分层推荐
输出四栏：
- 必装
- 强烈建议
- 可选
- 暂不建议

### 第三步：最后确认
“是否现在安装最小必要集？也可以只安装必装项，或暂时保持纯净环境。”

### 第四步（可选）：自动补装
如果用户明确授权自动补装：
- 仅自动写入 `opencode.json(c)` 中的 `plugin` 与 `mcp` 项
- GitHub Agent 仍需用户完成 GitHub App 安装与仓库工作流配置
- 写入前先检查配置是否为有效 JSON（避免 JSONC 注释导致解析失败）

## 8. 新增命令的实际价值

### `/audit-stack`
先看环境，避免盲装。

### `/recommend-stack`
根据当前项目目标给出最小安装集。

### `/deploy-readiness`
在正式部署前做最终结论，明确：
- 可直接部署
- 需补装关键项
- 需先清理冲突

---

## 9. 产品级验收标准
这次增强后，你的项目应该满足以下标准：

1. 用户第一次部署前，系统会先审计当前环境
2. 系统不会把任意 GitHub 仓库误判为“可直接调用”
3. 系统会优先推荐 OpenCode 内置能力，而不是盲目扩栈
4. 系统会给出“最小安装集”而不是一股脑全装
5. 系统在推荐后会明确询问用户是否安装
6. 推荐结果可以复查、解释和复现
